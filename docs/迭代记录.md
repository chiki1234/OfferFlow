# OfferFlow 迭代记录

本文档是项目迭代历史的单一记录入口，用于说明每一次可独立交付的迭代为什么发生、要解决什么问题、具体改变了什么，以及最终如何验证。

## 记录规则

1. 一次可独立交付并验收的功能新增、修改或删除记为一条迭代，不按 Git commit 数量拆分；同一迭代可以包含多个提交。
2. 开始实施时可以先创建“进行中”记录，完成实现和验证后更新为“已完成”或“部分完成”。
3. “背景”必填，并注明依据：
   - `用户明确提出`：原因来自用户的直接说明。
   - `故障或验收发现`：原因来自可复现问题、日志或验收结果。
   - `历史重建`：原因根据产品文档和提交历史整理，可能不包含用户未表达的个人动机。
   - `待用户确认`：现有资料不足；应向用户询问，得到答复后补齐，不把猜测写成事实。
4. 新增、修改、删除都必须逐项记录；没有发生的类型写“无”。同时记录数据迁移、兼容性、安全性和用户数据影响。
5. 验证结果只记录实际执行过的检查。受环境或配置阻塞的检查必须写明，不能记为通过。
6. 不在本文档中写入账号、密码、密钥、私有文件内容或其他敏感信息。
7. 新记录放在“历史记录”顶部，保持倒序排列。编号格式为 `ITER-YYYYMMDD-NN`，同一天从 `01` 递增。

## 条目模板

```markdown
## [ITER-YYYYMMDD-NN] 迭代名称

- 状态：进行中 / 已完成 / 部分完成 / 已取消
- 日期：YYYY-MM-DD
- 背景依据：用户明确提出 / 故障或验收发现 / 历史重建 / 待用户确认
- 背景：为什么需要进行本次迭代；现状、痛点或触发事件是什么。
- 目标：本次迭代完成后应达到什么结果。

### 变更详情

- 新增：新增的能力、页面、数据或规则；没有则写“无”。
- 修改：行为、交互、接口或规则的变化；没有则写“无”。
- 删除：移除的能力、入口、数据或兼容逻辑；没有则写“无”。

### 数据与兼容性

- 数据库迁移、数据修复、配置变化、兼容性、安全性及用户数据影响。

### 验证

- 实际完成的自动化测试、构建、人工验收或真实依赖验证。

### 遗留事项

- 未完成项、已知限制或后续动作；没有则写“无”。

### 关联变更

- Commit、PR、任务或主要文件；尚未提交时写“当前工作区”。
```

  > **信息分散**：不同求职信息散落在多个工具里。  
  > **关系断裂**：公司、岗位、JD、简历、任务、面试、录音、FAQ 之间没有形成关联。  
  > **维护成本高**：每次都靠我人工查找、关联、更新和判断，导致这套管理方式无法长期维持。
- 目标：确定一期领域词汇、数据事实、模块边界和技术选型，建立可以直接继续实现的工程骨架。
